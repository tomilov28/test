# Audit Remediation (A01-A12)

This document maps the phase-4/5 audit findings to the code changes made, the
tests that lock them in, and the machine evidence produced by the live runs.
Evidence JSON files referenced below live under `artifacts/<engine>/` and
`artifacts/<engine>/faults/`; they are regenerated by the Makefile targets
listed next to each finding.

Baseline commit: `425849e` (the audit was performed against this tree).
Remediation is the current tree; it is verified end-to-end by
`make fault-operaton` / `make fault-flowable` (Part A), `make measure-resources`
(Part B) and `make demo-operaton` / `make incident-operaton` etc. (Part C).

## A01 - Domain-first cancellation

**Finding.** Cancellation used to be dispatcher-driven: the API marked the
request, and the dispatcher decided the outcome when it reached the engine.
If the engine was down, the dispatcher either never got there or failed the
command, leaving the request's business outcome hostage to engine availability.

**Fix.** `app/api/routes.py::cancel_request` commits the business decision in
the *same transaction* that enqueues the `CANCEL_PROCESS` command:

```
BEGIN
  request.lifecycle_state = CLOSED
  request.outcome        = CANCELLED
  request.closed_at      = now()
  work_items              -> CANCELLED
  create WorkflowCommand CANCEL_PROCESS (PENDING)
COMMIT
```

The dispatcher (`app/workflow/dispatcher.py::dispatch_one`) is now a
technical-convergence step only: it never overwrites the outcome, and it
terminates the engine instance idempotently. The reconciler never closes a
request - an engine `ENDED` without a domain outcome is recorded as an
anomaly and the request stays `ACTIVE`.

**Sub-findings covered by scenarios** (`scripts/fault_scenarios.py`):

- `a01a` - cancel while the engine is down: request is `CLOSED/CANCELLED`
  immediately; convergence completes when the engine returns (no requeue
  needed). Evidence: `evidence/20260825T232057Z-cb35f54/operaton/fault-scenarios/a01a-domain-first-cancel-engine-down.json`.
- `a01b` - cancel while the engine outage outlasts the 5-attempt retry budget:
  the command reaches `FAILED` but the request stays `CLOSED/CANCELLED`.
  Recovery is the documented `/admin/commands/{id}/requeue`; after requeue the
  engine instance is terminated and the domain outcome is untouched.
  Evidence: `evidence/20260825T232057Z-cb35f54/operaton/fault-scenarios/a01b-cancel-exhausted-requeue.json`.
- `a01c` - cancel arrives before `START_PROCESS` is dispatched: the process is
  never started. If an earlier ambiguous attempt already created an instance,
  it is converged (terminated) so no orphan survives. Evidence:
  `evidence/20260825T232057Z-cb35f54/operaton/fault-scenarios/a01c-cancel-before-start.json`.

**Locked in by:** `tests/test_fault_injection.py::test_t14_lost_cancel_response_idempotent_termination`,
`tests/test_dispatcher.py` (A01/A01c), scenario scripts a01a/a01b/a01c.

## A02 - Domain-first completion

**Finding.** Human-task completion validated the outcome only when the command
reached the engine; an engine outage could strand a task that the domain had
already decided.

**Fix.** `app/domain/completion.py` defines the `CompletionContract` for the
`LONG_VISIT_POC` domain; `app/api/routes.py` validates it in the same
transaction that saves the `TaskResult` and enqueues `COMPLETE_TASK`. The
dispatcher completes the engine task only if it still exists (idempotent
convergence, A04) and never writes a business outcome.

**Sub-findings:**

- `a02a` - completion while the engine is down: the final domain action is
  committed immediately in the API transaction (`Request` -> `CLOSED`, outcome
  `COMPLETED`/`REJECTED`); the `COMPLETE_TASK` command stays `PENDING` and
  converges the engine task after the engine returns, without re-deciding the
  business outcome. Evidence:
  `evidence/20260825T232057Z-cb35f54/operaton/fault-scenarios/a02a-domain-completion-engine-down.json`.
- `a02b` - invalid completion contract (e.g. `final_decision` without
  `APPROVE`/`REJECT`) is rejected by the API. Evidence:
  `evidence/20260825T232057Z-cb35f54/operaton/fault-scenarios/a02b-invalid-completion-contract.json`.
- `a02c` - engine process ends without a domain outcome: the reconciler
  records an `engine_ended_without_domain_outcome` anomaly and leaves the
  request `ACTIVE` (no business decision). Evidence:
  `evidence/20260825T232057Z-cb35f54/operaton/fault-scenarios/a02c-engine-ended-without-outcome.json`.

**Locked in by:** `tests/test_completion.py`, `tests/test_fault_injection.py::test_t13`,
`tests/test_fault_injection.py::test_t15`, `tests/test_reconciler.py` (A02c).

## A03 - Outbox processing lease

**Finding.** Stale-command detection judged staleness against the claim
timestamp; a command claimed but not yet finished was compared against the
wrong base.

**Fix.** The lease is `processing_started_at`, set when the dispatcher claims
the command; a claim older than the lease timeout is re-armed to `PENDING`.
`created_at` is never used as the lease base.

**Verified against real PostgreSQL** (`tests/test_outbox_lease.py`,
`BENCH_DATABASE_URL` on a dedicated `benchmark_test` DB):

- A03a - a command created 5h ago but *claimed now* is NOT stale.
- A03b - two dispatcher threads claiming concurrently yield a single owner.
- A03c - a crash after claim (PROCESSING) is re-armed and dispatched.
- A03d - concurrent rearm + START never creates a duplicate engine instance.

## A04 - Idempotent convergence

**Finding.** At-least-once dispatch could double-start, double-complete, or
double-cancel after a lost response.

**Fix.** Every engine-mutating dispatch is guarded by a state check
(`app/workflow/dispatcher.py::dispatch_one`):

- `START_PROCESS` - query the engine by business key first; reuse the existing
  instance if one exists (no duplicate). A cancelled-before-start request
  terminates an ambiguous instance instead of starting.
- `COMPLETE_TASK` - complete only if the engine task still exists; otherwise
  the requested state is already achieved (success).
- `CANCEL_PROCESS` - cancel only if the instance is not `ENDED`.

**Locked in by:** `tests/test_dispatcher.py` A04 + A01c,
`tests/test_fault_injection.py` t12 (exactly one instance), t13, t14,
`test_invariants_single_instance_and_no_revert`.

## A05 - Fault controller semantics

**Finding.** The fault-injection controller's "exhausted" state was ambiguous:
an exhausted arm could fire again.

**Fix.** `_FaultSpec.is_active()` returns `remaining != 0`: `remaining == 0`
means inactive and never fires; `remaining < 0` fires forever; `remaining > 0`
fires that many times then stops. `maybe_wrap` only wraps an adapter while an
active arm exists.

**Locked in by:** `tests/test_fault_injector.py`; t12 arms `remaining=100`
(never expires - any second start would be hidden), t13/t14 arm `remaining=1`
(one hidden success), t15 arms `remaining=-1` (persistent failure).

## A06 - Engine-specific evidence collection

**Finding.** A single shared REST collector could not capture engine-specific
incident/job shapes.

**Fix.** `scripts/collect_artifacts.py` dispatches to engine-specific
collectors (Operaton external-task/incident/job endpoints vs. Flowable
dead-letter/job-management endpoints), then records a shared summary. The
collector call signature is uniform (`collector(client, external_client)`),
and the Flowable collector relies on the client base already carrying the
`/service` prefix (it does not add it a second time).

## A07 - Reproducibility

**Finding.** Scenario runs must be repeatable from one command and must leave
JUnit + logs behind.

**Fix.** `make fault-operaton` / `make fault-flowable`:

1. bring up the engine infra,
2. run the full integration suite with `--junitxml=artifacts/<engine>/fault-test-results.xml`,
3. run every scenario (R1-R5, stress, a01a-a02c; + deadlock for Flowable),
4. save `fault-suite.log`, `fault-scenarios.log` and regenerate the artifacts.

Both `fault-operaton` and `fault-flowable` redeploy the fixtures *between* the
pytest suite and the scenario runner: the integration suite drops its
`LONG_VISIT_POC` deployment in module teardown, and the scenarios must start
processes against a deployed fixture.

The integration suite is self-contained: `tests/test_fault_injection.py`
deploys its own `LONG_VISIT_POC` v1 fixture (it does not depend on another
module leaving a deployment behind), so run order does not matter.

## A08 - A down engine FAILS the run

**Finding.** A target engine that is down could produce a run with zero
tests (silent skip).

**Fix.** The module-scoped `engine` fixture in `tests/test_fault_injection.py`
calls `pytest.fail(...)` when the target engine is not reachable; the shared
`require_engine_fixture` in `tests/conftest.py` does the same for the other
integration suites. A down engine is a failed run, never a pass-by-skip.

## A09 - Authoritative reset

**Finding.** A reset that left stale data or stale engine DBs would poison
subsequent runs.

**Fix.** `make reset-state` stops app/workers/engines, drops the PostgreSQL
volume (`down -v`), recreates + migrates the app DB and recreates both engine
databases, then verifies via `stackctl check-stale`. Evidence of a clean
migration: `alembic upgrade head` runs the migration chain and the schema
version advances (`298bb5dfa5ff -> e1a2b3c4d5e6` in the latest reset).

Because a reset leaves the `operaton` engine database empty, the Operaton
container is configured with the official
`operaton.bpm.database-schema-update=true` property
(`OPERATON_BPM_DATABASE_SCHEMA_UPDATE` in `docker-compose.operaton.yml`), which
makes the engine create its schema idempotently on boot instead of relying on a
one-time bootstrap that does not reliably re-run after the volume is dropped.
`wait_for_engine.py` probes a process-engine-backed endpoint (e.g.
`/process-definition`) rather than the bare reachability probe, so "engine
ready" means the engine tables are actually queryable.

## A10 - No leftover processes

**Finding.** `stop-worker`/`make down` could kill the shared app or leave
orphan host processes behind.

**Fix.** `scripts/stackctl.py`:

- the FastAPI app is a shared process with a single pidfile/log
  (`artifacts/app.pid`, `artifacts/app.log`) - not engine-specific;
- process discovery is fingerprint-only (`scripts.worker --engine {engine}`,
  `uvicorn app.main:app`) so `stop-worker` can no longer match the app;
- `make down` terminates any leftover fingerprint match and `check-stale`
  verifies nothing survives.

Locked in by `scripts/fault_scenarios.py` R1-R5, which restart the app around
live engine state and assert no stale commands/duplicates afterwards.

## A11 - Clean Operaton baseline

**Finding.** The Operaton "Run" distro bundles an example module (invoice /
ReviewInvoice) that auto-deploys demo workload, polluting process-definition
and instance listings.

**Fix.** `docker-compose.operaton.yml` sets the official configuration property
`operaton.bpm.run.example.enabled=false` via the relaxed-binding env var
`OPERATON_BPM_RUN_EXAMPLE_ENABLED=false`, while keeping REST + Cockpit
unchanged.

**Verified live:** after a fresh stack, `/engine-rest/process-definition`
returns only the deployed fixtures (`LONG_VISIT_POC` x2 versions,
`credit_decision`), 0 running instances, and the engine log shows
`Invoice Example included - needs to be enabled in application configuration as well`.

## A12 - Authoritative image pinning

**Finding.** `:2.1.4` / `:8.0.0` tags are not enough; reviewers need the exact
image IDs and digests that were measured.

**Fix.** `scripts/collect_artifacts.py` records the image ID, size and
`RepoDigest`; `scripts/measure_resources.py` records `identity.container_id`,
`identity.image_id` and `identity.repo_digest` for each engine in
`artifacts/<engine>/resources.json`.
